# Integration Testing: A Rough Guide

Companion repository for the blog post [Integration testing: a rough guide](https://bakes.software/thoughts/integration-testing-a-rough-guide).

The post describes an approach to integration testing: real containers for stateful dependencies, request-level HTTP mocking for outbound service calls, everything wired up in-process. This repo is a minimal but runnable demonstration of those patterns.

---

## The Pattern

```
┌─────────────────┐   fetch (mocked by MSW)   ┌──────────────────────┐
│  order-service  │ ────────────────────────→ │  inventory-service   │
│  (PostgreSQL)   │                           │  (MongoDB)           │
└─────────────────┘                           └──────────────────────┘
        │
        ▼ in tests
┌──────────────────────────────────────────────┐
│  Real PostgreSQL (testcontainers)             │
│  Express app, booted in-process              │
│  inventory-service mocked via MSW            │
└──────────────────────────────────────────────┘
```

- **Real containers** for databases (PostgreSQL + MongoDB) via [testcontainers](https://testcontainers.com/)
- **MSW** intercepts outbound HTTP so order-service never needs a real inventory-service running
- **App factory pattern** (`createApp(deps)`) lets tests inject a real DB and a fake HTTP client without any process management
- **Orval** generates typed clients, MSW handlers, and mock factories from OpenAPI specs

## Prerequisites

- Node.js 20+
- pnpm (`npm install -g pnpm`)
- Docker (running - required for testcontainers)

## Quick Start

```bash
git clone <this-repo>
cd integration-testing-a-rough-guide

pnpm install

# Generate SDK packages from OpenAPI specs (required before running tests)
pnpm codegen

# Run all integration tests
pnpm test
```

Expected output: 11 passing tests across two services.

## Project Structure

```
packages/
  order-service/          # Express + PostgreSQL
  │  openapi.yaml         #   ← source of truth for the order-service API
  │  migrations/          #   ← SQL run against the testcontainer DB
  │  src/
  │  │  app.ts            #   ← createApp(deps) - the app factory
  │  │  routes/orders.ts  #   ← calls inventory-service via injected client
  │  test/
  │     global-setup.ts                #   ← starts PostgreSQL container once per run
  │     helpers.ts                     #   ← creates isolated DB + MSW + boots app per suite
  │     orders.integration.test.ts     #   ← create/get order tests
  │     list-orders.integration.test.ts #  ← list/filter tests (separate DB!)

  order-service-sdk/      # Generated from order-service/openapi.yaml
  │  orval.config.ts      #   ← Orval config
  │  src/fetcher.ts       #   ← committed: configurable fetch wrapper
  │  src/index.ts         #   ← committed: barrel
  │  src/generated/       #   ← gitignored: generated by `pnpm codegen`

  inventory-service/      # Express + MongoDB (leaf service, no outbound calls)
  inventory-service-sdk/  # Generated from inventory-service/openapi.yaml
```

## Codegen

Each `*-sdk` package has an `orval.config.ts` that reads the corresponding service's `openapi.yaml` and generates:

| File | Contents |
|------|----------|
| `src/generated/client.ts` | `getInventoryService()` factory returning typed axios wrappers |
| `src/generated/client.ts` (same file) | MSW v2 handler factories (`get*MockHandler`, `getInventoryServiceMock`) |
| `src/generated/client.ts` (same file) | Response mock factories (`get*ResponseMock`) |
| `src/generated/model/` | TypeScript interfaces (one per schema) |

Axios is used as the HTTP client (Orval's default). The generated functions call a configured axios instance, so you get `{ data, status, headers }` from every response with no extra adapter code.

Run codegen: `pnpm codegen` (or `pnpm --filter '*-sdk' codegen`)

The generated files are gitignored - commit the `openapi.yaml`, not the output.

## Key Patterns

### App factory (`src/app.ts`)

The `createApp(deps)` pattern is what makes in-process testing work. Tests call it with a testcontainer-backed DB; the inventory-service URL is configured separately via `configure()` from the SDK, which MSW then intercepts. Production `server.ts` does the same with a real URL.

The routes use the generated `getProduct` from `@repo/inventory-service-sdk` directly - no hand-written client interface. If inventory-service changes its API, the TypeScript import breaks at compile time.

### Container lifecycle (`test/global-setup.ts`)

One container per test run, started before any test file executes. Vitest's `globalSetup` hooks ensure this. After starting the container, migrations run once on a template database - test suites clone this template instead of re-running migrations each time.

### Database isolation (`test/helpers.ts`)

Each test file clones the template database - a single PostgreSQL operation that copies the entire schema without re-running migrations. The order-service has two test files (`orders.integration.test.ts` and `list-orders.integration.test.ts`) that each call `setup()` - each gets a fresh clone, so seed data in one file never leaks into the other. Teardown drops the clone entirely.

### MSW setup and teardown (`test/helpers.ts`, `test/*.test.ts`)

Default handlers from the generated SDK cover all endpoints. Tests override specific handlers per-test and reset after each one.

## Adding a New Service

1. Create `packages/my-service/openapi.yaml`
2. Create `packages/my-service-sdk/orval.config.ts` pointing at it
3. Add `"codegen": "orval --config orval.config.ts"` to the SDK's `package.json`
4. Add `src/fetcher.ts` and `src/index.ts` to the SDK (copy from an existing SDK)
5. Run `pnpm codegen`
6. Wire the SDK into consuming services as a `workspace:*` dependency

## Troubleshooting

**`POSTGRES_TEST_URI not set - did globalSetup run?`**
Docker is not running, or testcontainers couldn't start a container. Check `docker info`.

**`Container took too long to start`**
First run pulls the Docker image. Subsequent runs are fast. Increase `testTimeout` in `vitest.config.ts` if needed.

**`Module not found: @repo/inventory-service-sdk`**
Run `pnpm codegen` - the `src/generated/` directory is gitignored and must be generated locally.
